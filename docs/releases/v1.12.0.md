# Find an element without reading the whole page

Chrome Control MCP 1.12.0 lets an agent find the element it wants without reading the whole page,
and makes the page it does read a third the size.

## browser_find

Agents act on elements by ref, and until now a ref came only from `browser_snapshot` -- the whole
page, every time. `browser_find` returns just the elements that match, in the snapshot's own line
format with the same refs, so "find the button, then click it" costs a few hundred bytes:

- `text` looks for words in an element's name or value; `query` takes the same as a phrase, where a
  role word such as "button", "link" or "field" filters by role (`"Send message button"`); `regex`
  takes a pattern. `role` and `max_results` narrow it further.
- The best match comes first, each followed by the dialog or landmark it sits in, and marked
  off-screen when it is. With no match, the reply names the closest names on the page.
- Its refs work with every element tool straight away, and are refused after the page navigates,
  exactly as a snapshot's are. Matching is code, not a model.

Measured on Wikipedia's "Web browser" article: 1.3 KB for a find, against a 38 KB snapshot.

## Snapshots a third the size

Every outline now leaves out repetition -- a text line that repeats its parent's name, Chrome's
inline text runs, wrappers around a single line, and indentation for nesting it does not show. The
line format is unchanged. Measured whole snapshots:

| Page                             | 1.11.1 | 1.12.0 |
| -------------------------------- | -----: | -----: |
| Wikipedia, "Web browser"         | 113 KB |  38 KB |
| Hacker News                      |  71 KB |  18 KB |
| GitHub, microsoft/playwright-mcp | 138 KB |  48 KB |

All three are now under the 50,000 characters past which Claude Code saves a reply to a file
instead of showing it.

`browser_snapshot` also takes options: `ref` reads one region -- landmarks, dialogs, forms, tables,
lists and articles carry refs for it -- `depth` limits levels, `filter` keeps the interactive
elements (15 KB on that article) or what is on screen (9 KB), and `max_chars` caps the outline by
collapsing the largest off-screen regions to one line each, naming the ref that reads them, rather
than cutting the end off.

## Reads in pages

`browser_read` returns 30,000 characters at a time by default, with `total` and the `next_offset`
to continue from; `max_chars` goes up to 200,000. `ref` or `selector` reads one element, and
`mode: "main"` the page's main content. The reply is the same JSON as before.

## A smaller catalog

The tool list a client keeps in every prompt is 42,951 bytes for 54 tools, from 44,965 for 53, and
the same bytes on every listing.

## Compatibility

- The full profile has 54 tools and the read-only profile 15. A client with an explicit tool
  allow-list sees `browser_find` once it is added there.
- `browser_read` returns 30,000 characters where it returned up to 200,000; the reply says where to
  continue.
- An extension older than 1.12.0 keeps working; `filter: "viewport"` and read's `ref`, `selector`
  and `mode` ask to reload it.

## Updating

The extension reloads itself into this version once no agent is using it; coming from 1.8.x, press
reload on Chrome Control MCP at chrome://extensions once. Restart any editor or agent that was
running before the update, so it starts the new server -- between tasks, since a server restarting
closes the tabs its agents opened.
