# A managed install no longer reports a registration mismatch

Chrome Control MCP 1.11.1 stops a managed install from telling agents to re-register a server that
is already registered, and builds from source on the newest Linux toolchains.

## Fixed

- **No false "registered to a different server" note.** On a managed install -- the one
  `--install`, the VS Code extension or `browser_update_apply` puts in place -- a browser tool
  called before the extension had attached said Chrome's native-messaging host was registered to
  another server, and told the agent to call `browser_extension_install`. That changed nothing:
  the registration names the install's stable `current` link, the server reported the version
  folder behind it, and the note compared the two paths as text when they are the same file. It
  now compares the files the paths lead to, through the directory junction a managed install uses
  on Windows too. A registration that names a missing file, or a different copy of the server, is
  still reported.
- **Builds with GCC 16 and Qt 6.12.** GCC suspected the PNG header reader screenshots use of
  reading past an empty buffer, on a path already ruled out, and `-Werror` stopped the build. The
  reader now goes through Qt's bounded operations. Released binaries, built with Qt 6.10, were not
  affected.
- **Tests build with newer GCC.** Two test files contained an invisible bidirectional character,
  which GCC's `-Wbidi-chars` refuses. They now build it from its code point, and a pre-commit hook
  refuses those characters in any tracked text file.

## Updating

The extension reloads itself into this version once no agent is using it; coming from 1.8.x, press
reload on Chrome Control MCP at chrome://extensions once. Restart any editor or agent that was
running before the update, so it starts the new server -- between tasks, since a server restarting
closes the tabs its agents opened.
