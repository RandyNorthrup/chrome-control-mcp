# Faster actions, and screenshots the size a model uses

Chrome Control MCP 1.14.0 makes clicks, hovers and scrolls in the agent's tab take milliseconds
instead of up to three seconds, and returns screenshots at the size a model actually reads.

## Actions in milliseconds

An agent works in a tab of its own, behind the one you are using. Chrome draws a tab that is not in
front about once a second, and it acknowledges a mouse event or a scroll only when it draws, so an
action could wait a second or more for each step. While an action runs, the extension now keeps the
agent's tab drawing with a one-pixel screencast, and stops it when the action is done.

Measured on Linux, in the tab behind the user's:

| Action          | 1.13.0       | 1.14.0       |
| --------------- | ------------ | ------------ |
| Scroll by ref   | 2.0 to 3.1 s | under 100 ms |
| Click, at worst | 1.06 s       | under 60 ms  |
| `browser_tabs`  | 26 ms        | about 2 ms   |

A click or hover on an element already in view also skips the scroll-into-view it used to wait
for, and replies from the browser reach the server as soon as they arrive instead of at the
relay's next 25 ms look. A new live suite holds every scroll, click and hover under half a
second.

## Screenshots: a view, a zoom, and a file for people

- **A view by default**: one image pixel per CSS pixel, long edge at most 1,568 -- the size Claude
  shrinks any larger image to before it reads it. On a 2x display that is a quarter of the bytes.
- **Zoom for detail**: pass `ref`, or `x`/`y`/`width`/`height` in view pixels, to get that part of
  the page at up to the device's own pixels. A zoom never scrolls the page.
- **`purpose: "presentation"`** saves the device's own pixels as a lossless PNG and replies with
  its path, for screenshots meant for people. The read-only profile refuses it, since it writes a
  file. `CHROME_CONTROL_MCP_OUTPUT_DIR` chooses the folder; by default it is `ChromeControlMCP` in
  Downloads, beside `browser_print`'s PDFs.

`browser_click_at`, `browser_hover` and `browser_drag` take view pixels, fractions included, and
`browser_box`'s `screenshot_center` gives them to a tenth -- so a point read off the view, or worked
out from a zoom, lands where it was read.

## Recordings

`browser_record_start` keeps the page's shape instead of stretching it to 1280x800, and takes
`resolution: "full"` for the device's own pixels.

## Fixed

- A screenshot of a tab being recorded stopped the recording's frames.
- A full-page screenshot cut at Chrome's 16,384-pixel limit now says so in the reply.
- A popup one agent's click opened could be taken by another agent, the one whose tab you had in
  front. Chrome names the tab in front as the opener of a link opened from a background tab; the
  browser's record of which page opened a tab is now the only one believed.

## Updating from 1.13

Nothing to do. Screenshots that an agent reads are smaller and click coordinates follow them; an
agent that read pixel positions off a 1.13 screenshot on a high-density display should take a new
one. The Chrome Web Store build updates itself once Google has reviewed this version.
