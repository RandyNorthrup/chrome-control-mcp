Chrome Control MCP 1.5.2 fixes four faults that only a real browser could find.

1.5.1 repaired the identity check that stopped the bridge attaching at all. With
it attaching, the first things it tried were broken — and every one of them had
been green in the test suite the whole time.

## browser_navigate never navigated

It answered, every time, that your URL was not http(s):

```
navigate requires an http(s) URL.
```

`dispatchCommand` builds each handler's arguments positionally:

```js
const params = [session];
if (entry.tab) params.push(await activeTabId(session));
if (entry.args) params.push(args);
```

`handleNavigate` was still declared `(tabId, args)`. It received the session as
its tab id and the tab id as its arguments, read `args.url` off a number, found
`undefined`, and refused. Broken since 1.5.0, when the session was threaded
through the worker so that several editors could each have one.

The refactor that introduced it was made verifiable with ESLint: delete a
binding, and `no-undef` names every line that used it. That technique cannot see
this. `handleNavigate` never mentions `session`, so removing it from the
parameter list left nothing undefined — JavaScript simply passed the arguments
along one place to the left.

All 41 handlers the command table names directly were audited against the
dispatcher's contract. `navigate` was the only one. The check is now a test:
every entry's declared arity is compared with what the dispatcher will hand it,
with a guard so it cannot pass vacuously against an empty table.

## Recording never recorded

`browser_record_start` failed on its first real start:

```
canvas.captureStream is not a function
```

The offscreen document built an `OffscreenCanvas`. `captureStream()` is defined
on `HTMLCanvasElement` and does not exist there. Having a DOM is the entire
reason that document exists — the service worker has none — and the code then
reached for the one canvas that is not part of it.

Nothing caught it because `browser/extension/offscreen.js` was the one shipped
file no test loaded. The recording suite stubs the document out and tests the
worker's side of the conversation, which is a reasonable seam and left the
encoder with no coverage at all. It has a suite of its own now, whose harness
gives the context an `OffscreenCanvas` with no `captureStream`, exactly as
Chrome does. Against the old code it reproduces the production error verbatim.

## An orphaned relay held the bridge shut

Reloading the extension closes the relay's port. The relay spends nearly all its
life blocked reading the pipe, waiting for the server to send a command, and
from there Chrome going away is invisible: nothing wakes that read. The process
stayed alive holding its end of a pipe created with `nMaxInstances = 1` — the
anti-squatting property that lets exactly one client connect — so every relay
Chrome started afterwards was refused:

```
Cannot open the bridge pipe (err=231)
```

231 is `ERROR_PIPE_BUSY`. The bridge stayed down until the orphan was killed by
hand, and an extension reload produced one every time.

The relay now watches its own standard input and ends the process when Chrome
lets go. Two properties matter. It **peeks and never consumes**, because the
pump reads that same descriptor on another thread and a check that took a byte
would steal part of a frame. And it is **one-sided**: only a definite hangup
counts, so a relay run from a console — where the check fails for an unrelated
reason — is not killed by a guess.

It arms at relay start rather than after the handshake. The pump is where an
unnoticed Chrome is fatal, but every earlier phase can strand a process too, and
there is no phase in which carrying on without a browser is the right answer.

Ending the process is the whole repair. The relay holds no state worth saving —
every id, ref and session lives in the MCP process — and Chrome starts a new one
on the next port connection.

## Two editors could not share the browser

The feature 1.5.0 was built for worked only while the first session happened not
to hold the tab in front.

`sessionWindow()` answers which window a session is working in. Every caller
wants only the id: which window to list, to resolve an index against, or to open
a tab in. It got one by calling `activeTab()`, which **adopts** the user's active
tab as the session's and refuses when another session already holds it. So the
second editor was told:

> That tab is being driven by another Chrome Control MCP session (server 26124).
> Choose a different tab, or open one with browser_new_tab.

and `browser_new_tab` failed the same way, for the same reason. The advice and
the refusal were the same call.

Asking which window now reads the window directly and takes no tab from anyone.

## What this says about the tests

Four faults, all shipped green. Three of them sat in places the suites were
structured not to reach: a file that was stubbed rather than loaded, a parameter
list that no reference could contradict, and a process lifetime that only a real
port closing can exercise. The fourth was a lease check doing its job in a place
that should never have asked it.

Each now has a test that fails against the code as it shipped, and the live
evidence is recorded in `docs/VERIFICATION.md` rather than summarised here.

## Upgrading

`browser_update_apply` as usual, then restart the MCP server in your client and
reload the extension at `chrome://extensions`. Neither Chrome nor your editor
reloads code underneath a running process.

`--install` now reports whether it copied anything. It is a no-op when the
version is already installed and already current — which is right, because the
VS Code extension calls it on every activation — but it answered `ok` either
way, so a rebuilt tree of the same version looked installed when nothing had
moved.
