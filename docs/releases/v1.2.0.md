Chrome Control MCP 1.2.0 closes the last thing a person still had to do by hand in a browser the
assistant was otherwise driving: attaching a file.

## Added

- **`browser_upload` attaches local files to a page's file input.** The page receives real `File`
  objects and runs its own `input` and `change` handlers, so a site that reads `files[0]`, previews
  the image, or submits the form sees exactly what the user's own file picker would have given it.
  Pass a ref from the latest snapshot and absolute paths; more than one path needs an input marked
  `multiple`.

  This was previously documented as impossible, and the reason was real: CDP's own file API,
  `DOM.setFileInputFiles`, answers "Not allowed" to an extension's debugger session. It is possible
  another way. The bytes are delivered to the tab and a function running IN the page builds the
  `File` and assigns it through a `DataTransfer` -- ordinary web platform behaviour, no privileged
  API, nothing Chrome forbids. Files cross the bridge in pieces, because Chrome carries at most
  1 MiB in a single message from a native host, and the extension holds those pieces only until the
  upload is applied.

## Security

This is the one tool that reads the user's disk, and it is treated that way:

- Absent from the read-only profile.
- `CHROME_CONTROL_MCP_UPLOAD_ROOTS` confines it to named directories when set. Paths are made
  canonical first, so a symlink or a `..` cannot point inside a root and read outside it, and a
  sibling directory whose name merely begins with a root's name is not inside it.
- A path must be absolute and name a real file. A file is bounded at 16 MiB, a call at 8 files.
- No path reaches the extension or the page. The page gets the file's name, type, and bytes; where
  it came from stays on the server side.
- Buffered pieces are dropped when the upload is applied and whenever the session ends, so a
  half-delivered file never outlives the session it belonged to.

See [`docs/SECURITY.md`](../SECURITY.md) for the profile and the variable.

## Verified

Windows 11 Pro 26200, MSVC 19.50, Qt 6.10.0, Node 24.13.0, Chrome for Testing 153.0.8010.52.

- 10/10 native and extension suites, including a new `test_browser_uploads`: a file returns whole
  and byte-identical, a large file is cut into pieces that each fit the bridge and rejoin exactly,
  relative and missing paths and directories are refused, the file limit holds, and a configured
  root cannot be escaped by a lookalike sibling or a `..`.
- 59 service-worker unit cases, 7 of them new: pieces reassemble in any arrival order, a missing
  piece assembles to nothing rather than a hole, pieces that disagree about their count are
  refused, and ending a session drops every buffered byte.
- Live E2E on real Chrome: **44/44 tools across 153 reversible cases**. The upload case writes a
  temporary file, attaches it, and then asserts what the PAGE read back -- name, size, and the
  file's own bytes -- rather than what the tool claimed.

Upgrade: replace the executable and the unpacked `extension` folder, then reload the extension once
from `chrome://extensions`. No native-host re-registration is needed; the manifest and extension ID
are unchanged.
