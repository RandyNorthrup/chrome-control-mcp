Chrome Control MCP 1.3.1 makes one dead end explain itself. Everything 1.3.0 added is unchanged;
this is about what the program says when it cannot reach the browser.

## Fixed

- **"The extension is not attached" now says when the real reason is two copies of this program.**
  Chrome starts whichever executable its native-messaging registration names. When that is not the
  copy serving MCP -- a build directory beside an installed one is enough -- the relay Chrome
  starts refuses the bridge, correctly, because a bridge served by a different image is exactly
  what that check exists to refuse. The operator was then told only that the extension was not
  attached, which is true and impossible to act on. The refusal now names the registered
  executable, names the one serving, says that Chrome starts the registered one, and says to call
  `browser_extension_install` on the server that is running.

- **The relay's own message no longer implies an impostor.** It said "not the Chrome Control MCP
  binary" about a process that usually WAS that binary, just another copy of it. It now names both
  images. When the serving process cannot be read at all -- it exited, or the pid never existed --
  it says that, rather than claiming a mismatch of paths it never observed.

Neither check changed. Both still fail closed; only what they report changed.

## Verified

Windows 11 Pro 26200, MSVC 19.50, Qt 6.10.0, Node 24.13.0.

- 10/10 native and extension suites, with four new cases: the note names both executables and the
  fix; it stays silent when the registration already names the running server, when the paths
  differ only cosmetically, when nothing is registered, and (on Windows) when they differ only in
  case; the installer reports the registered executable and reports nothing when there is no
  registration; and the relay's mismatch text names both images or reports an unreadable process.
- Reproduced end to end before and after: with the registration pointing at one copy and another
  copy serving, the old build answered "not attached" and the new build answered with both paths
  and the command to run.

Upgrade: replace the executable. The unpacked extension is unchanged from 1.3.0 apart from its
version string, so a reload is optional; no native-host re-registration is needed.
