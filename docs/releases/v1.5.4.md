Chrome Control MCP 1.5.4 fixes a fault that could make any tool taking a `[ref]`
act on the element beside the one the model named, and report success.

## A ref named a position, not a node

`browser_snapshot` advertises "a stable `[ref]`". It was not stable. Refs were
numbered by document order and renumbered from scratch on every snapshot, so an
element that gained a ref-worthy sibling **above** it answered to a different ref
the next time the page was captured. Every ref a model was still holding went on
resolving — silently, and to the element next door.

The header said as much without noticing: interactable nodes got "a stable `eN`
ref in document order". Those two halves contradict each other. In document order
is exactly what makes a ref unstable. The advertised contract was the honest half,
so the code now meets it.

This reached `browser_click`, `browser_type`, `browser_drag`, `browser_scroll` —
anything resolving a ref. A click could land on the wrong control and the reply
would say it worked.

### What changed

The previous snapshot's index is carried into the next one by `backendNodeId`. A
node seen before keeps the ref it was issued; only a genuinely new node takes a
new number; and a node that has gone takes its ref with it rather than leaving it
for whoever stands in that position next. Nothing is carried across a navigation,
where a `backendNodeId` no longer names the same node.

### How it was found

The live suite's nested-region scroll had been failing on macOS for several
releases, reporting `scrolled: {x:0, y:0}` — which a caller could not tell from
"already at the edge". Three plausible explanations were tested and killed:

- **The wheel does not take on macOS.** A pure-CDP probe on the macOS runner moved
  the region 180px in 25 of 25 runs, across five dispatch shapes.
- **The box is read while the page is still scrolling.** Zero drift between
  `DOM.scrollIntoViewIfNeeded` and the box read that follows it, on every platform.
- **The page moved under the point.** The point was byte-identical before and
  after re-resolving it.

What found it was making the reply carry evidence instead of a verdict. Once
`browser_scroll` reported what the wheel landed on and how much travel was under
it, the first failure said `hit: "DIV#shadow-host"` and `room: 0` — and the ref's
own box came back 131×15, which is the fixture's shadow **button**. The scroll
region is 1021×126. The suite had been driving the wrong element all along.

## Also fixed

**An action could be aimed at where an element used to be.** Bringing an element
into view moves the page, and that move is not always finished when the command
that asked for it returns. `resolveActionQuad` now waits for the page to come to
rest before reading the box. Shared by click, hover, drag and reveal.

**A scroll by `[ref]` now checks that its point still lands on the element.** If
the point has slipped, the box is taken again; if it has slipped twice, the scroll
is refused and names what it hit, rather than wheeling a stranger and reporting the
element that was asked for. The hit test climbs shadow boundaries: `elementFromPoint`
reports the **host** for a point inside a shadow tree and `Node.contains` stops at
the boundary, so a plain containment test calls every element in a shadow root a
miss.

## New in the reply

`browser_scroll` now returns `point`, `hit` and `room` alongside `scrolled`.
`scrolled` 0 with `room` 0 is an edge already reached, and an answer. `scrolled` 0
with room left means the wheel never reached the scroller, which is a fault worth
reporting rather than an answer.

## Also in this release

`tools/scroll_probe.mjs`, the diagnostic that ruled out the wheel and the protocol.
It is pure CDP — no MCP server, no extension, no build — so it runs in about two
minutes wherever a platform disagrees about input.

## Upgrading

`browser_update_apply`, then restart the MCP server in your client and reload the
extension at `chrome://extensions`.
