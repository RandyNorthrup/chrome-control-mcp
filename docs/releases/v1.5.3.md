Chrome Control MCP 1.5.3 corrects what the recording tool tells an assistant, and
brings the README in line with what the code actually does. No behaviour changes.

## A sentence that was never true

`browser_record_start` described itself to models like this:

> Starting a second recording for the same session is refused; stop the first.
> Chrome shows its own recording indicator while this runs.

The last sentence was wrong on the path that shipped. It survived from the
`chrome.tabCapture` design, which was ruled out before any code was written:
tabCapture needs the `activeTab` grant, and that comes only from a user invoking
the extension on that specific tab, which an agent-driven start has no way to
produce.

What shipped instead is CDP `Page.startScreencast` on the debugger the session
already holds. That raises no recording indicator. What Chrome shows is the
debugging banner, and it is up for the whole session whether or not anything is
being recorded.

`docs/SECURITY.md` had this right — it says Chrome "displays its own indicator
while a tab is being debugged" — but the description a model reads did not, and
that is the one an assistant would repeat to a user.

## The README

**A claim the code does not make.** The capability table said a session "never
takes your OS focus". It never _asks_ for focus, which is not the same
statement. `docs/VERIFICATION.md` has recorded since 2026-09-18 that Hyprland
focuses a newly mapped window regardless, and `browser_window new` reports that
as `took_os_focus` precisely so it is not silent. The table now says what the
code promises and names the case where the compositor overrules it.

**Two capabilities that were listed and never explained.** Multi-session and
recording appeared in the capability table and nowhere else. The README now
says how a second editor gets a tab (`browser_new_tab` opens one in the
background and makes it that session's), what happens when it asks for a tab
another session is driving (refused by name, and marked
`controlled_by_other_session` in `browser_tabs` rather than hidden), the two
recording tool names, what `browser_record_stop` returns, and why the video
cannot come back through a tool reply.

**New screenshots.** The old pair was three weeks old, and the same file was
used twice — once as the hero image and again as the first cell of "See it
work". The replacements were captured by two MCP servers attached at the same
time: one driving the public playground, one driving the local E2E fixture in a
tab of its own. That makes them evidence of the multi-session behaviour rather
than two captures taken separately and presented as a pair.

## Checked while writing, and left alone

The 49-tool count and the 12 tools in the read-only profile were taken from the
binary rather than from the previous README. CMake 3.25, Qt 6.5, Node 20.19,
Chrome 116 in the extension manifest, the three install roots, the environment
variable names, the extension id, the native-host name, "no TCP listener"
(the only listener is AF_UNIX), the 44/44 live-tool figure and the 35/35 display
matrix under both the Windows and macOS sections all check out against the code
and the recorded evidence.

One claim cannot be illustrated: the controlled tab sits in a pink **AI CONTROL**
tab group, and `browser_screenshot` captures the page viewport only, so no
screenshot can show browser chrome. It is verified live instead — a tab listing
reports `"group": "AI CONTROL"` for the session's tab.

## Upgrading

`browser_update_apply`, then restart the MCP server in your client and reload the
extension at `chrome://extensions`.
