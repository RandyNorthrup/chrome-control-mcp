Chrome Control MCP 1.1.1 is a fix for the one call that could end a session. A screenshot of a tab
nobody is looking at never came back, and taking it down with it went the whole bridge -- on the
very tab this project puts the assistant in by design. It is fixed, and the platform that found it
now runs the suites that found it.

## Fixed

- **A screenshot of a background tab returns.** Chrome answers `Page.captureScreenshot` only once
  the tab produces a compositor frame, and a tab that is not the front tab of an on-screen window
  produces none. The capture never answered, the app waited out its whole 30 s transport deadline,
  and the reset that followed detached the extension: one screenshot ended the session, and the
  next call found no browser at all. A capture of a tab that is not on screen now runs with a
  one-pixel screencast, which is what makes Chrome composite that tab, and every capture path is
  bounded well inside the transport deadline -- so a screenshot that truly cannot be taken, such as
  one of a minimized window, is a single failed call on a bridge that is still up.

  The forced path returns the same image, not a different one. Measured at 2x: a foreground plain
  capture and a background forced capture are byte-identical, 114,526 bytes for the viewport and
  178,520 for the full page. On the E2E fixture in a background tab, a capture that gave no reply
  in 30 s and left the extension detached now answers in 1.3 to 1.8 s.

## Changed

- **The live suites' dedicated browser runs on Windows.** It refused to, on the grounds that
  Windows keeps native-messaging registrations in the registry rather than per profile. The
  registration already names the executable under test, and `CHROME_CONTROL_MCP_RUNTIME_DIR` is
  what keeps each browser to its own server, so the run now asserts that the user's registration
  names the executable under test and proceeds. This is what found the capture hang: a dedicated
  browser on Windows hides a background tab, where the macOS one did not.
- **`browser_extension_install` states that its remaining step is manual and cannot be automated.**
  Loading an unpacked extension is the user's to do: branded Chrome 137 and later ignore
  `--load-extension`, policy installation wants a Web Store listing this project does not have, and
  driving the browser's own windows is not an install path. The tool's description and its reply
  now say so, as do the README and `docs/TOOLS.md`, so an assistant reading only the tool's own
  text hands the step to the user instead of looking for a workaround that does not exist.

## Verified

Windows 11 Pro 26200, MSVC 19.50, Qt 6.10.0, CMake 4.4.3, Node 24.13.0, Chrome for Testing
153.0.8010.52.

- 9/9 native and extension suites; 52 service-worker unit cases, 9 of them new and covering the
  capture path: what counts as on screen, that an on-screen tab is captured with no screencast,
  that an off-screen one is captured with frames forced and the cast always stopped, and that a
  bounded wait never leaves an unhandled rejection behind.
- Live on Chrome, every call in a tab nobody was looking at: **43/43 tools, 151 reversible cases**,
  Chrome state restored.
- Live display matrix in dedicated browsers, now on Windows too: **35/35 configurations,
  3,335/3,335 checks** across display scales 1x-3x, windows from 390x844 to 3840x2160, every Chrome
  zoom step from 25% to 500%, pinch at 1.5x, 2x, and 3x, and both scrollbar kinds.
- Live user-interference suite: **10/10 checks**.
- Formatting, ESLint, and `npm audit` clean.
- Full evidence is in `docs/VERIFICATION.md`.

Upgrade: replace the executable and the unpacked `extension` folder, then reload the extension once
from `chrome://extensions`. No native-host re-registration is needed; the manifest and extension ID
are unchanged.
