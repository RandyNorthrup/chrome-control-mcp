# Large uploads

Chrome Control MCP 1.11.0 lets an agent upload files of the size people actually post: a channel's
long videos, not just documents.

## Up to 2 GiB a file

`browser_upload` was bounded at 16 MiB a file. A video channel's long uploads run to hundreds of
megabytes, and since 1.8.0 an agent's click catches the page's file dialog, so filling the native
picker by hand was no way round it either.

Now a file goes from the disk to the page a piece at a time. The server reads it as it sends it, and
each piece goes straight into the page that will use it, where it gathers until the file is
complete; then the page is given it exactly as before -- to the file input or drop zone a ref names,
to the input picker the page opened, or as the answer to `showOpenFilePicker`. Neither the server
nor the extension holds the file whole. Measured: a 300 MiB file reaches the page byte for byte.

Delivery runs at the pace of Chrome's extension debugger channel, measured at 2 to 6 MB/s, so a
390 MB video takes one to three minutes. The call holds the server meanwhile, as every call does,
and a client that times calls out sooner than that needs a longer timeout for large files.

## Setting the bound

The default is 2 GiB a file. Set `CHROME_CONTROL_MCP_UPLOAD_MAX_MB` in the server's environment to
change it -- a whole number of MiB from 1 to 8192:

```text
CHROME_CONTROL_MCP_UPLOAD_MAX_MB=512
```

A value that is not one of those falls back to 16 MiB, and a refusal under it says so. A file over
the bound is refused before any of it is sent, naming its size, the bound and the variable.
`CHROME_CONTROL_MCP_UPLOAD_ROOTS` still confines which files can be sent at all.

## When a delivery cannot finish

If the page navigates, or the tab is let go, while a file is arriving, the page gets nothing and the
reply says why; upload again once it has loaded. A file that changes on disk while it is being sent
is refused rather than sent half old and half new.

## Also fixed: a relay ending itself mid-session

On Linux and macOS, the relay between Chrome and the server checks four times a second whether
Chrome has closed its end. That check could mistake a busy connection for a closed one -- about one
look in 2,000 under steady traffic -- and end a working relay in the middle of a session: the
"relay closed the connection" error seen rarely before, and often during a long upload. It now
takes three closed looks in a row.

## What stays as it was

- An extension older than 1.11.0 carries at most 16 MiB a file; a larger one is refused with a note
  to reload the extension at chrome://extensions.
- Files put on a clipboard with `browser_clipboard` stay at 16 MiB each: a clipboard holds them
  whole until a paste.
- No path reaches the extension or the page.
- `browser_navigate` opens `http` and `https` URLs only, as before, and now says that
  `javascript:`, `data:` and `file:` are refused.

## Updating

From 1.9.0 the extension reloads itself into this version once no agent is using it; coming from
1.8.x, press reload on Chrome Control MCP at chrome://extensions once. Restart any editor or agent
that was running before the update, so it starts the new server -- between tasks, since a server
restarting closes the tabs its agents opened.
