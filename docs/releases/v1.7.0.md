Chrome Control MCP 1.7.0 fixes the three things 1.6.1 shipped without fixing, and the reason all
three had survived: not one of them had a test that could fail. It also fixes something nobody had
filed, because the people it bothered would sooner turn the extension off than report it.

## `browser_scroll` reported 0 for a container it had just moved

The two reads either side of the wheel matched scrollers by name, and the name counted ancestors
upward from whatever element the point happened to land on -- `scroller-2:DIV`. That number belongs
to the **content** under the point, not to the container. Scroll the content and the point lands
somewhere else inside the same scroller -- on its padding, on a taller row, on a child one level
deeper -- so the container that had just moved came back under a different name. `scrollDistance`
matched by name, found nothing from before, and reported `scrolled 0` for a scroll it had performed.
The in-page rest detector compared the same list and saw a change that was only the renaming.

Scrollers are named by their path from the document root now. What is under the point may change;
where the container sits in the document does not. The live fixture's scroll region gained rows of
differing depth so the rename actually happens there, and the suite checks the distance the reply
claims against the measured movement of an element inside it.

That last part took two attempts. The first version measured across the same call that reported the
distance -- but aiming at a ref reveals it first, and on that call the reveal scrolled the page 726px
before the wheel moved the container 180px. Both numbers were right; the comparison was measuring
two scrolls against one. It measures across a second scroll now, whose reveal has nothing left to do.

## Elements the page wires up itself had no ref

A real page builds most of its controls out of plain elements: a `<div>` with a click handler, a card
that is clickable because it is styled `cursor: pointer`. None of that reaches the accessibility
tree. Those arrive as `generic` with no name and nothing saying they can be acted on, so the capture
dropped them -- the model was shown scenery where the page had a button, and the only way to reach
one was `browser_click_at` with a pixel read off a screenshot.

The capture reads three signals out of the DOM snapshot it already takes, so this costs no extra
round trip:

| Flag          | What earned it                                           |
| ------------- | -------------------------------------------------------- |
| `(clickable)` | Chrome's own `isClickable`                               |
| `(hoverable)` | a pointer handler attribute on the element               |
| `(pointer)`   | its computed cursor is `pointer` and its parent's is not |

Both halves of that were measured against a real Chrome before anything was built on them, and both
mattered. `isClickable` flags an inline `onclick` **and** an `addEventListener` wiring, which no
attribute scan could see -- but it does not flag a hover-only handler, which is why the attribute
scan is still there. And `cursor` is inherited: a child inside a pointer card computes `pointer`
itself, so promoting on the computed value alone would have turned one clickable card into a ref for
every part of it. Comparing against the parent is what keeps the ref on the card.

An element laid out to nothing gets no ref however it is wired. There is nothing to aim at.

## `browser did not reply within 30000 ms (connection reset)`

A silence budget was being spent as a work budget. Handlers are allowed far longer than 30 s by
design -- `browser_download` polls to 120 s -- so a slow page, a big download or a loaded machine
surfaced as a transport failure and a reset connection for work that was proceeding normally.

The extension reports progress every 5 seconds while a command runs. The relay forwards those beats
without mistaking one for the reply, and each restarts the server's deadline. Silence still fails in
30 seconds. A command that beats but never finishes is abandoned at 180 s with a refusal that names
it and says it ran too long, instead of blaming a connection that is fine.

The beat earns its keep twice: posting on the port is activity, so the same beat that reports the
work keeps the MV3 service worker doing it alive.

Deciding which of the two budgets ran out turned out not to be a clock comparison. The deadline is
built from whole milliseconds of remaining time, so a read cut short by the ceiling expires a
fraction **before** it -- measured on Linux, seven beats in -- and a clock check then says the
ceiling had not been reached. It is decided by which budget sized the read instead.

### And the half the beats could not reach

CI then lost a 5120x2880 screenshot to the same message the beats were built to prevent. The beats
were not at fault and were not even involved: once the extension starts posting a reply there are no
more beats to send, and the stall was in the transfer itself. The read loop handed every chunk of an
incoming frame the same shrinking deadline, so the budget bounded the whole transfer rather than a
gap in it -- a reply of a few megabytes crossing a loaded machine simply ran out of time while
arriving perfectly steadily.

A chunk that moved bytes now restarts the budget, bounded by the same ceiling on the whole exchange.
Silence still fails in 30 seconds. The regression test dribbles one frame across in ten pieces over
three times the budget and requires it whole.

One thing fell out of that. `browser_wait_for` clamped `timeout_ms` to 25 seconds, and its comment
said exactly why: the whole exchange lived under one 30-second deadline, so a wait allowed to outlast
it left the caller reading a transport reset while the handler kept polling into a relay that was
already gone. That was the right workaround for the budget as it was. The budget restarts now, so the
cap is the same 120 seconds `browser_download` uses -- and the description says so, which it did not
when a caller asking for 60 seconds silently got 25.

## A scroll could report that it had settled before it had

The rest detector resolved when the serialized offsets **differed** from the ones read before the
wheel. But the chain under the point changes composition as content moves, so a scroller entering or
leaving it made a different list without anything having moved -- while `scrollDistance`, which
matches only the names present in both reads, correctly reported 0.

So `browser_scroll` could answer `settled: true, scrolled: 0` and the page would go on moving after
the reply had been sent, leaving the next call to read a stale position. Both now measure by one
rule, in one function that travels into the page beside the reader that produces the offsets.

## The extension asked for a bridge that was not there, forever

Nobody filed this one. Every connection attempt starts a process: `connectNative` makes Chrome launch
the native host, which looks for a published server, finds none, says so and exits. The retry was a
flat 2 seconds re-armed by its own disconnect, with one further attempt on every `tabs.onUpdated` and
`tabs.onActivated` -- so a machine with the extension installed and no editor running spawned host
processes continuously, and faster while its owner was browsing.

The interval now doubles while nothing answers, from 2 seconds to a 2-minute ceiling, and resets the
moment a bridge answers. A server that is running is still found within two seconds. The first retry
after a failure is still fast, because a server that has only just gone may be a moment from coming
back; it is the run of failures after that which earns the waiting. The tab events and the alarm are
held to the same interval, which is the part that matters -- they fire far more often than any timer,
and they were never subject to the old one.

Backing off is not the same as being able to stop, so the toolbar button is now a switch. Click it
while the bridge is connected and it pauses: the ports close, the browser is released, and nothing
reaches for it again until you resume. Click while paused and it resumes and connects at once; click
while it is merely not connected and it retries immediately rather than waiting out the interval. The
badge reads `off` while paused and shows nothing otherwise. The state survives a browser restart --
somebody who turned it off because it was in their way should not find it back on tomorrow.

This adds the `storage` permission.

## `browser_extension_uninstall` had never been run

Not by the live suite, which cannot remove the registration it is using, and not by a unit test,
which stops at the installer class and never reaches the tool. What made it untestable on Windows was
the registration being one fixed key per user: POSIX has had `CHROME_CONTROL_MCP_NATIVE_HOST_DIR`
from the beginning, Windows had no equivalent, and the only key to test against was the user's own.
`CHROME_CONTROL_MCP_NATIVE_HOST_KEY` and `CHROME_CONTROL_MCP_DATA_DIR` are that missing half. Chrome
still reads only the fixed key; what these buy is a way to run install and uninstall for real without
touching it.

The new suite installs, checks the registration through the operating system rather than through the
code that wrote it, uninstalls, and checks it is gone -- then asserts the user's own registration is
exactly as it was, because a test that deletes a registration for real has to prove which one.

It found something on the first run. Removing a registration that was never there succeeds at the
system-call level on both platforms -- a missing key and a missing file are not errors -- so the reply
said "Browser extension bridge unregistered" for a machine it had not changed. A caller checking
whether the bridge was still wired up would have read that as proof it had just been taken apart. It
answers "Nothing to unregister" now.

## Upgrading

`browser_update_apply`, then restart the MCP server in your client and reload the extension at
`chrome://extensions`. The reload is required this time rather than merely advisable: the progress
beats and the new permission both live in the extension.
