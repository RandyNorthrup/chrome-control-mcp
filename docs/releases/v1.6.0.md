Chrome Control MCP 1.6.0 lets a session see what the page said and what it
fetched, runs the live browser suites on Windows for the first time, and gives
recording the end-to-end coverage it shipped without.

## A session could not see why anything failed

An agent that clicked a button and saw nothing happen had no way to learn that
the page threw `TypeError: x is not a function`. That one fact usually explains
it, and nothing in the toolset could reach it.

**`browser_console`** reports the page's own console output, its uncaught
exceptions and unhandled rejections, and what the _browser_ said about the page —
a blocked mixed-content load, a CSP violation, a subresource that failed. That
last group never reaches the page's console API at all, so without it a page that
simply does not work gives no reason why.

**`browser_network`** reports the requests the page made: method, URL, resource
type, status, MIME type, and the milliseconds until the response arrived. A
request that never got a response carries the browser's error text instead of a
status, because a transport failure has no status and `0` would read as a server
answering `0`. The Network domain was already enabled and in-flight requests were
already tracked — for `wait_for network_idle` — but none of it had ever been
surfaced, so nothing could confirm that a form actually posted.

Both are bounded rings of bounded entries, because every field in them is written
by the site. Each reply separates what _it_ left out (`omitted`) from what the
buffer discarded (`dropped`): an empty list means "the page was quiet" in one case
and "the errors scrolled off" in the other, and those lead somewhere different.
`browser_network` also reports `in_flight`, so an empty list is not read as a page
that asked for nothing.

Neither can change what the page does or what the user sees, so both are in the
read-only profile.

## Why there is still no JavaScript evaluation tool

It is the obvious thing to add, and it is written down in `docs/TOOLS.md` and
`docs/SECURITY.md` as a decision rather than left as an omission.

An arbitrary-evaluation tool would void most of the defenses in `SECURITY.md` in
one call: it reads and writes storage outside the isolated world that verifies the
live origin, redefines `window.confirm` past the dialog policy, clicks with none
of the freshness gating that `[ref]` and coordinate actions require, answers the
refusal of `javascript:` URLs through another door, and can delete the AI CONTROL
overlay that is the user's only signal a session is driving the tab.

It cannot be narrowed into safety either: there is no read-only
`Runtime.evaluate`, so a "read-only eval" would be a promise the code could not
keep. `browser_console` and `browser_network` answer what evaluation is usually
reached for. `browser_js_click` remains the one narrow escape hatch.

## The live suites run on Windows

They ran on macOS alone. Linux is excluded because that runner never answers a
capture under an emulated fractional scale; Windows was simply never in the
matrix.

Windows is where the versioned install layout lives — `current` is a directory
junction onto `versions/<version>` — and that is exactly what shipped broken in
**1.4.0 and again in 1.5.0**, with green unit tests throughout, because nothing
ever drove a live browser there. The job registers the native-messaging host for
the build under test, since Windows keeps one such key per user and the dedicated
browser reaches whatever it names.

Getting it running took one real fix: the job configured with `-G Ninja` and no
MSVC environment, so CMake took the first `c++` on the runner's PATH — MinGW —
and the build died on `-Wsign-conversion` in code MSVC compiles silently. It now
asks for the Visual Studio generator, as the existing build job already did.

## Recording has live coverage

It shipped in 1.5.0 and the suite said so in its own `NOT_EXERCISED_HERE`:
_"needs its own live coverage; not written yet"_. That is how a start which failed
on its first real call — `captureStream` on an `OffscreenCanvas`, which has none —
reached a release. The case now records, checks that a second start is refused,
stops, and asserts the file is not the zero-byte one a recorder that captured
nothing writes.

Nothing in `NOT_EXERCISED_HERE` now says "not written yet".

## Three bugs the new coverage found

None of these could have been caught by a unit test.

**The network log filled with icons.** The media element's controls load a `data:`
URL per button, and they crowded out every request the page actually made — the
first live run saw a log that was nothing but base64 SVG. Inline content is bytes
the page already had: no connection, no server, no status worth reporting. It is
still counted for `network_idle`, which must wait for it, and left out of the log.

**Entries were written too late.** Recording at `loadingFinished` lost the
document's own request every time, because that request completes the navigation
which drops anything still awaiting a response — and a `fetch()` whose body is
never read never finishes loading at all, so it sat in flight for the life of the
session. Entries are now written when the response arrives, which fixes both, and
`ms` became what the server took rather than what the body cost to stream.

**A fixture left a request outstanding**, and `wait_for network_idle` correctly
refused to report idle three cases later. That one was the product catching the
test.

## Also

The control cursor is 24px rather than 32px. At that size the SVG renders at scale
1, so the arrow's tip lands on exact integers instead of the rounding the old size
needed, and the cheap position-only update and the full overlay build now share
one offset — a test asserts they agree, because which of them draws depends only
on whether the overlay already existed.

## Upgrading

`browser_update_apply`, then restart the MCP server in your client and reload the
extension at `chrome://extensions`.
