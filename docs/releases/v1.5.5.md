Chrome Control MCP 1.5.5 fixes a drag that could take the extension's service
worker down with it, and puts a gate under the version drift that had been
shipping unnoticed since 1.4.0.

## A failed drag could stop the session answering

A drag sends every step's commands before it awaits any of them. That is
deliberate: a mouse move is a continuous event that Chrome answers at a frame,
and awaiting each one in turn measured 8.9 s for a single drag in a background
tab, against 0.23 s in a foreground one.

The cost of doing it that way was never paid for. A command that rejects while an
earlier step is still being awaited has no handler attached yet, and V8 raises
`unhandledrejection` at the next microtask checkpoint — which, in a service
worker, is something the runtime may tear the worker down over. The drag then
stops answering, and the bridge reports what it can see:

```text
browser_drag failed: browser did not reply within 30000 ms (connection reset)
```

That names the transport for a fault in the handler. The macOS display matrix
failed exactly this way.

Each in-flight command is now marked handled the moment it is created. The
originals are still awaited in order, so a real mid-drag failure still stops the
drag where it stopped and still releases the mouse button where the pointer
actually got to.

## A drag rebuilt the whole cursor overlay on every step

Positioning the "AI CONTROL" cursor re-sent the script that builds the entire
overlay: three `getElementById` lookups, a stylesheet check, two `cssText`
assignments and an `innerHTML` that reparses an SVG. That is the right thing to
do once. A drag did it on every step, up to 60 of them, for the sake of two
numbers.

There is now a position-only nudge that moves a cursor already on the page and
reports `false` when there is none, with the full build kept as the fallback for
a fresh document. A drag had already come within the bridge's 30 s reply budget
on a loaded runner; this was the per-step cost inside it.

## Both lockfiles said 1.3.1

`package-lock.json` and `vscode/package-lock.json` named version 1.3.1 while the
project shipped 1.4.0, 1.5.0, 1.5.1, 1.5.2, 1.5.3 and 1.5.4. Five releases went
out carrying a lockfile from before any of them.

Nothing caught it because nothing had ever compared the places a version is
written, and npm does not do it either: `npm ci` validates dependencies against
the lock, not the root version, so the drift is silent by construction. The
release checklist was a person remembering six files.

`tests/test_release_versions.mjs` is that checklist, run by the gate. Every file
that states a version must state the same one — CMake, both `package.json`s, both
lockfiles, the extension manifest and the installer header — and the version being
shipped must have a changelog entry and a release note to go with it.

## Upgrading

`browser_update_apply`, then restart the MCP server in your client and reload the
extension at `chrome://extensions`.
