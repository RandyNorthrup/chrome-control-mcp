# One extension for Chrome Control MCP and S.A.K. Utility

Chrome Control MCP 1.16.0 lets the Chrome Web Store extension serve S.A.K. Utility as well, each
application through its own native host, once an administrator turns that on; and it fixes three
ways a call could do what it did not ask for.

## Two applications, one extension

The extension can also connect to S.A.K. Utility's native host, `com.sak.browsercontrol`, so a
technician with S.A.K. Utility uses this same extension rather than a second one. It does so only
while Chrome's policy for the extension holds `sakHostEnabled: true`, which only an administrator
can set: S.A.K. Utility, which runs as one, sets it when its Browser Control is turned on and
removes it when it is turned off. A program that registers a host of that name without that policy
gets nothing. The two applications never meet:

- each sees only its own sessions, tabs and windows: the other's tabs are left out of every
  listing, count and numbering, and a tab the other holds is refused exactly as an id that names
  no tab is;
- no command reaches the other's tab, by id, by index, through the active tab, or by closing its
  window;
- every reply goes back to the application that asked, and nothing is passed from one to the other;
- the profile's identity (its account email) is told to Chrome Control MCP only, never to S.A.K.
  Utility (a tab's title is page content: a page that puts the email in its title shows it to
  either);
- while one holds a tab on a site, the other may not read or change that site's cookies or site
  settings, nor, through a neighbouring site, a cookie that is also sent to it (a sign-in cookie of
  the domain above); otherwise those belong to the Chrome profile and are shared, like its sign-ins;
- S.A.K. Utility's tabs sit in groups named "S.A.K. ...", Chrome Control MCP's in "AI ..." as
  before.

The toolbar button still stops everything: it pauses both.

## Nothing changes without S.A.K. Utility

On a computer without S.A.K. Utility the policy is not set, and the extension never asks for its
host. Where it is set but the host is missing (or its program is gone), the extension asks at
startup, then after ten minutes, then after waits that double up to six hours, and says nothing
about it. Chrome Control MCP's own connection is exactly what it was.

## Fixes

- `browser_window` focus or close with `window_id: null` asked about window 0 and was then refused
  as "not in the listing"; it now says a window id is needed.
- `browser_download` with `timeout_ms: null` waited one second instead of the 30-second default.
- `browser_group_tabs` with a colour Chrome does not know grouped the tabs and then reported a
  failure; the colour is now refused before anything is grouped.

## Updating from 1.15

Nothing to do. The extension updates from the Chrome Web Store, or with the unpacked folder of
this release; the server is unchanged apart from its version.
