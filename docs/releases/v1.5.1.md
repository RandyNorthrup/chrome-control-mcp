Chrome Control MCP 1.5.1 fixes a Windows bug that stopped the bridge attaching at all.

## One file, two names

On a Windows managed install every relay refused every server:

> The bridge is served by `...\versions\1.5.0\chrome_control_mcp.exe`, but this relay is
> `...\current\chrome_control_mcp.exe`. Chrome starts the executable named in its native-messaging
> registration, so re-register from the server you are running.

The advice was sound for the fault it was written for -- two different copies of the program, one
serving MCP and another registered with Chrome -- but that was not this fault. Both processes were
the same file, started from the same path.

`current` is a directory junction onto `versions/<version>`, and the identity check asked two
different questions without noticing. A process asked about ITSELF with `GetModuleFileNameW`, which
reports the path it was launched through, and about its PEER with `QueryFullProcessImageNameW`,
which reports what that path resolves to. Through a junction those are two spellings of one file.
Each side compared them, found a stranger, and closed the connection.

The check is symmetric, so both directions failed: the relay refused the server before the
handshake, and the server would have refused the relay after it.

## What else it broke

The same comparison answers a second question -- is the process that published this rendezvous
record still alive and still one of ours. With the comparison always false, every OTHER server's
record looked abandoned. Servers swept each other's records as stale and republished their own, so
the multi-session support released in 1.5.0 spent its time undoing itself. That is visible in a
record's timestamp moving without its owner having done anything.

## The fix

The POSIX half had been right since the versioned layout landed, and said why:

```
// Canonicalize both sides: one of them can arrive through a symbolic link
// (an install reached through `current/`), and comparing the raw paths would
// then call our own process a stranger.
```

The Windows half never got that. It also existed twice -- once in the pipe server, once in the
relay -- in copies that could drift without anything failing to build. Both are now one module,
`windows_process_identity`, which asks about this process and about a peer through the same call
and canonicalizes the answer, so a junction, a short (8.3) path component or a difference in case
cannot make one file look like two.

## Why no test caught it

Every existing test ran the binary from where it was built. The asymmetry only appears when the
process doing the asking was ITSELF launched through the junction, which no test arranged and no
build-tree run ever does. It became reachable the moment 1.5.0's self-update put both the MCP
command path and the native-host registration behind `current`.

`test_windows_process_identity` now builds a real junction, re-launches the test binary through it,
and has that child -- standing exactly where the relay stands -- decide whether the parent is the
same program. Against the pre-fix code that answer is "no" and the test fails, which is what makes
it worth having.

Its teardown removes the junction as a link, never recursively. The first version of the test used
`QTemporaryDir`, whose recursive cleanup followed the junction and deleted the contents of the build
directory it pointed at.

## Upgrading

`browser_update_apply` as usual. Afterwards restart the MCP server in your client and press reload
on the extension at `chrome://extensions`: neither Chrome nor your editor reloads code underneath a
running process, and until the server restarts it keeps serving the old build.
