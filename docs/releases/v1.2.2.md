Chrome Control MCP 1.2.2 is the 1.2.0 feature on a commit that passes every gate. The two releases
between them each failed one analyzer on a line added with that feature, and a released commit
should be green.

## Fixed

- The roots test in `browser_uploads.cpp` searched with a raw loop rather than `std::any_of`,
  failing the `cppcheck` gate on the 1.2.1 commit. No behaviour changes.

This release's whole subject is what 1.2.0 added, described in
[`docs/releases/v1.2.0.md`](v1.2.0.md):

- **`browser_upload` attaches local files to a page's file input**, as the user's own picker would.
  The page receives real `File` objects and runs its own `input` and `change` handlers, so a site
  that reads `files[0]`, previews the image, or submits the form sees what a human choice gives it.
- The DevTools file API refuses an extension's debugger session, so the bytes are delivered to the
  tab and a function running IN the page builds the `File` and assigns it through a `DataTransfer`.
  Files cross the bridge in pieces, because Chrome carries at most 1 MiB in one message from a
  native host.
- It is the one tool that reads the user's disk: absent from the read-only profile, confined by
  `CHROME_CONTROL_MCP_UPLOAD_ROOTS` when set, bounded at 16 MiB a file and 8 files a call, and
  sending no local path to the extension or the page.
