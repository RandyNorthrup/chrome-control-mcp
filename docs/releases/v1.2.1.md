Chrome Control MCP 1.2.1 is 1.2.0 with one loop variable typed correctly. The 1.2.0 commit failed
the `clang-tidy` gate on a line added with the upload feature, and a released commit should be
green, so this release carries the same program past the same gates.

## Fixed

- The loop reading `browser_upload`'s paths bound a `QJsonValueConstRef` to a `const QJsonValue &`,
  which converts through a temporary on every element. No behaviour changes.

Everything 1.2.0 added is in this release. Its notes are in
[`docs/releases/v1.2.0.md`](v1.2.0.md):

- **`browser_upload` attaches local files to a page's file input**, as the user's own picker would.
  The page receives real `File` objects and runs its own `input` and `change` handlers.
- It is the one tool that reads the user's disk, so it is absent from the read-only profile,
  confined by `CHROME_CONTROL_MCP_UPLOAD_ROOTS` when that is set, bounded at 16 MiB a file and
  8 files a call, and sends no local path to the extension or the page.

## Verified

Rebuilt and re-run at 1.2.1 on Windows 11, MSVC 19.50, Qt 6.10.0, Node 24.13.0: 10/10 native and
extension suites, 59 service-worker unit cases, `clang-tidy` clean over the changed sources, the
whole pre-commit gate set clean, and a live E2E of **44/44 tools across 153 reversible cases** on
real Chrome. Full evidence is in `docs/VERIFICATION.md`.

Upgrade: replace the executable and the unpacked `extension` folder, then reload the extension once
from `chrome://extensions`. No native-host re-registration is needed; the manifest and extension ID
are unchanged.
