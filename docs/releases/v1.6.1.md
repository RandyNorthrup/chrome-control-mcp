Chrome Control MCP 1.6.1 fixes everything a fresh-install run on a clean Windows
11 VM turned up: an agent installed 1.6.0 there and drove 50 of the 51 tools
against live sites, checking each one's _effect_ rather than its reply. Six faults
and three inaccurate descriptions came back. This is all of them.

## `browser_network` dropped redirects

A redirect re-fires `Network.requestWillBeSent` under the **same** request id, and
the pending entry was overwritten without ever being logged. A form POST that 302s
appeared only as the GET that followed — the exact opposite of the one thing the
tool exists for, confirming that a form actually posted.

Both hops are logged now. The one that redirected carries its own status and a
`redirected_to` naming where it went; the request it landed on stays its own
entry. The E2E fixture gained a `POST /api/redirect → /api/landed` route and the
live suite asserts both.

## `browser_select` could not match a label from the snapshot

Plenty of pages write `&nbsp;` between words for alignment. That puts U+00A0 in
`option.text` while the snapshot renders an ordinary space, and a `===` comparison
makes those two different strings — so `"Los Angeles"`, copied straight out of the
snapshot, never matched the option literally called that. Both the single and the
multi-select paths now compare with whitespace collapsed.

## `browser_permission` passed a value Chrome rejects

`javascript`, `images` and `popups` are on-or-off: there is no prompt to show, so
the API refuses `ask` rather than treating it as a default. The tool handed it
straight through, and what came back was:

```text
Invalid invocation: Error at property 'setting': Value must be one of allow, block.
```

That names neither the tool, nor the permission, nor what would have worked. The
per-type table is checked before the call now, and the refusal says all three. It
also states the limitation honestly: Chrome's extension API **cannot** return one
site to the browser default — that belongs in `chrome://settings/content`.

## `browser_media` could not reach some videos

A `<video>` whose controls the page draws itself is not focusable and carries no
accessibility value, so it earned no ref and reached the model as scenery it could
see and not touch — while the video beside it, which happened to be focusable,
worked. That is why it looked arbitrary. `video` and `audio` are interactable
roles now, which is what a tool built to drive them requires.

## `browser_hover` could not reach an element without a ref

A link with no `href`, or a div with only an `onmouseenter` handler, has no
accessibility role that says interactable. `browser_click_at` already answered that
for clicks by taking a pixel off the last screenshot; hover had no such path, so
those elements were clickable and not hoverable.

It takes `x`/`y` on the same terms now — refused unless the screenshot they came
from still matches the live render — and refuses a call that gives both a ref and
a point.

## Three descriptions that did not match the code

- The recording timeline's field is `cmd`; the description called it `name`.
- `browser_back` can fail after a `browser_navigate` nobody clicked on, because
  Chrome creates no history entry for a navigation with no user interaction. That
  refusal is Chrome's, and the description now says so instead of leaving it
  looking like a fault.
- `browser_extension_install` told every caller to load the extension by hand even
  when it was already loaded and connected. It now says which case it means.

## A failure that could not be read

The Linux display matrix died with `SyntaxError: Unexpected token 'b', "browser
di"... is not valid JSON` — a tool that failed under load being handed to
`JSON.parse`. A reply that is not JSON now reports what the tool actually
answered. This does not stop the underlying reply-budget timeout; it makes the
next one legible.

## Upgrading

`browser_update_apply`, then restart the MCP server in your client and reload the
extension at `chrome://extensions`.
