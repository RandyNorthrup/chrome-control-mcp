Chrome Control MCP 1.5.0 lets more than one agent drive the browser, and adds recording.

## More than one agent

Two editors open on two projects each got an MCP server, and only one of them got the browser. The
second stood down -- "Another Chrome Control MCP server already owns the browser bridge" -- and
served its native tools with browser control off until the first exited. That was deliberate, and it
was the single most common thing to run into.

The limit was not really the transport. It was that the extension's service worker kept one
session's state in module-level variables: the CDP attachment, the adopted tab, the DOM generation,
the snapshot tab and epoch, the screenshot transform, the tab and window listings, the dialog arm,
the command generation, the network-idle set, the emulation and auth overrides, the upload buffer.
Every one of those is a correctness guard, and two agents sharing them would not have failed loudly.
They would each have invalidated the other's view of the page and carried on: a tab index that named
something else by the time it was used, an element ref pointing into a document that had been
replaced.

Those twenty-six are now fields of a session record, and the worker holds a set of them -- one per
native port, one port per server. Each port's listeners close over their session, so an arriving
frame never has to be matched back to one by searching. Only the browser's own events need routing,
because they name a tab and nothing else: a debugger detach goes to whichever session holds that
attachment, a new tab to whichever adopted its opener.

### Keeping them apart

A transport that served several clients without leases would have been the worse half of this
change. Two agents would appear to work while corrupting each other's view of the page, which is
harder to notice than a refusal.

So a tab is leased by the session that adopted it or has a debugger attachment on it, and the second
session to reach for it is refused by name -- `browser_select_tab` on a tab another session is
driving says so, rather than failing as though the tab were gone. Tabs held elsewhere are marked in
`browser_tabs` rather than hidden: the operator can see the whole window either way, and a listing
that gave no reason for the refusal would read as a bug.

Chrome already allows one debugger client per target, which covers everything that goes through the
DevTools protocol. The lease is what covers `chrome.tabs`, `chrome.windows`, cookies and downloads,
where Chrome would let two sessions collide without complaint.

### How a relay finds its server

Rendezvous records are named for the process that published them -- `browser_bridge-<pid>.json` --
so several servers can advertise at once. The identity is in the file name rather than a
subdirectory because the POSIX socket lives in that same directory and its path has to fit
`sockaddr_un`; a nesting level would spend that budget for nothing.

The relay no longer computes a path. It lists what is published, offers the list to the extension,
and connects to the one the extension names. The relay speaks first, as it already did with
`bridge_ready`, because the extension has no filesystem access and so has no server to name until it
is offered one -- and because a frame sent unprompted would be read by an older relay as the reply to
a command it had not yet sent, putting every later exchange one step out of phase. Chrome does not
reload an unpacked extension when its files change, so that pairing is the normal case after an
update.

A server the extension asks for that is no longer published yields no connection rather than a
substitute: attaching a session to a server it did not choose is worse than reporting the bridge
unavailable.

Records left behind by servers that exited are swept when a server starts. A single shared record
never needed that -- it was simply overwritten by whoever published next.

## Recording

`browser_record_start` records the session's tab to a `.webm`; `browser_record_stop` ends it and
returns where it was saved. Video only; there is no audio.

The video never comes back through a tool reply. The bridge is one command, one reply, with hard
caps on the reply -- 16 MiB for a screenshot, 8 MiB for text -- so a recording of any length could
not fit through it. Stop returns a path, the way `browser_download` does.

Beside the video it writes `<name>.timeline.json`: every command that ran while recording, with its
id, its name, its offset in milliseconds, and the DOM generation at that moment. That is the
machine-readable half, and it needs no second encoder -- it is what lets the frames be read against
what drove them.

### Why not chrome.tabCapture

Tab capture is the obvious API for this and it cannot be used. Chrome's documentation is explicit:
capture "can only be called after the user invokes an extension, such as by clicking the extension's
action button", and "only tabs for which the extension has been granted the `activeTab` permission
can be used as the target tab". That grant comes from a user invoking the extension on that specific
tab. An agent-driven start has no such invocation, and `<all_urls>` does not substitute.

Frames come from the DevTools protocol instead -- `Page.startScreencast`, on the target this session
is already attached to, the same channel every click and snapshot already uses. It needs no gesture
and no permission this extension did not already hold. The cost is video only, and frame pacing that
is whatever CDP delivers rather than a true fixed rate.

The one permission recording adds is `offscreen`, for a hidden extension page to run the encoder in;
`MediaRecorder` needs a DOM and the service worker has none. It grants no access to the user's
browsing. `debugger` was already held and is strictly more powerful than tab capture would have
been. Chrome shows its own indicator while a tab is being debugged.

Chrome allows exactly one offscreen document per extension, so the recorder inside it is a map keyed
by session and every message to it names the session it is for. There is no "current recording" --
a value meaning that would be wrong the moment a second session started one.

### What it refuses

Both are refusals rather than silent substitutions, because both alternatives lose work without
saying so:

- **A second start for the same session** is refused. Restarting would discard the first recording
  with no way to tell it had happened.
- **Changing tabs while recording** is refused. A recording follows one tab, and ending it because
  the operator changed tabs would lose the video to an action they could have done in the other
  order. `browser_select_tab`, `browser_new_tab` and `browser_window new`/`focus` refuse;
  `browser_window close` does not, because it does not retarget the session.

If the session ends while recording -- the bridge drops, the tab closes, DevTools detaches -- the
recording is **discarded**, not finalized. The frames stop arriving and the encoded bytes cover only
part of what was asked for, so writing them out would hand back a file that looks complete and is
not.

## Fixed

- A browser-initiated detach now releases what a deliberate one does. `detachAll` cleared thirteen
  things; the `onDetach` listener cleared ten. The three it forgot were the three with no symptom at
  the moment they went wrong: a polling handler kept driving a tab nothing was attached to until its
  own timeout expired, a User-Agent captured from a page the session no longer drove could be
  restored over the next one, and a half-delivered upload survived into the next session.

- Two installs running at once can no longer corrupt each other. An exclusive cross-process lock on
  the install root spans each whole check-and-change; without it, two updaters shared one staging
  directory name and could overwrite each other's partial download -- so the checksum that proved the
  first could be checked against the second.

## Changed

- The full profile advertises 49 tools; the read-only profile still advertises 12. Recording is
  absent from read-only.

## Verified

Windows 11 Pro 26200, MSVC 19.50, Qt 6.10.3, Node 24. Linux via WSL, GCC, Qt 6.11.2.

- 17/17 native and extension suites on Windows and Linux, including four suites written for this
  release: the transport handshake, session teardown, multi-session leasing, and recording.
- 110 JavaScript tests over the service worker, which is evaluated exactly as shipped.
- ASan+UBSan 17/17. clang-tidy and exhaustive cppcheck clean over the whole compile database.
- Two servers running at once, each publishing its own record, with the second no longer standing
  down -- checked against the real binaries, not only the tests.
- A relay driven through the new offer exchange against a real server: it offered the published
  server, took the answer, and connected to that record.
- A planted record naming a dead process is swept when a server starts.

Red drills, each run against deliberately broken code and each failing its own test: a lease check
that never refuses, a surplus port that reconnects forever, a release that forgets a live recording,
an extension that stays silent on an empty offer, one that speaks unprompted, and a relay that
substitutes a server the extension did not ask for.

The recording encoder itself runs in an offscreen document, which the unit harness cannot host. What
is covered there is everything the worker owns -- the refusals, the state, the timeline, and the
messages it sends the recorder. The encoder is exercised by the live browser suites.
